# Development dual-factor password reset

Migration 009 and OpenAPI 0.5.0 complete the selected primary-contact OTP plus pre-enrolled 128-bit recovery-code policy for email and telephone accounts. The existing RecoveryEnrollmentEnabled opt-in controls enrollment, initiation and completion. Development-only, real-user release remains blocked.

POST /auth/password/reset/complete requires the authenticated BFF/subject and operationId, challengeId, bindingSecret, six-digit code, uppercase 32-hex recoveryCode, and a 15–128-character newPassword. No Bearer Session or caller-supplied verified flag is accepted. Both proof comparisons are constant-time; failure is the same UNAUTHORIZED response. Five failed presentations per Person per fixed fifteen-minute window are shared across challenges and replay; creating a fresh challenge does not reset that counter. Each fresh challenge permits five presentations. Invalid password policy is rejected before any fence. Counter transactions finish before the Person gate; Argon2 runs without locks.

Under the Person gate, proof expiry, contact binding, enrollment version, unreserved code, epoch, readiness and unchanged Credential evidence are checked again. The shared password-change admission writes a ResetPassword intent and sealed recovery/replay Argon2 material, reserves the code, advances epoch once and closes Sessions/families atomically. OTP delivery material is erased on acceptance. Credential replacement and its immutable receipt/PasswordChanged outbox commit independently without holding a Session lock. The selected event context is documented in RESET_EVENT_DECISION.md.

Only receipt-backed Reconciled releases the fence. Applied consumes the reserved code and queues PasswordResetCompleted once; terminal RejectedNotApplied releases its reservation without consuming it. FailedClosed preserves both fence and reservation until private operator recovery obtains a receipt; no timeout or force unlock exists. New login with the new password reports recoveryEnrollmentRequired=true. Re-enrollment requires a fresh active Session at the reset epoch, current-password proof and explicit loss acknowledgement; a database trigger rejects an older Session. BFF must require replacement before ordinary use.

Identical lost-response replay is bound to client, operation, challenge and both original factors with a purpose-specific MAC containing no password. The new password is compared against sealed Argon2 material outside locks. Replay cannot outlive the original ten-minute challenge. Accepted challenge/receipt evidence is retained; expiry never undoes an accepted operation or blocks its worker reconciliation.

## Initiation storage and contention

Unknown, unenrolled, ineligible, fenced and budget-denied initiation stores only a deletable ten-minute decoy. Known eligible challenges keep immutable bindings; unaccepted expired challenges and their delivery/attempt rows are deleted. Worker cleanup removes at most 100 decoys and 100 eligible unaccepted challenges per tick. Accepted challenges are retained by their immutable acceptance foreign key. Sustained-volume storage monitoring and historical accepted-operation retention remain release work.

The per-Person three-deliveries/fifteen-minute budget is reserved in an autocommit transaction before taking the Person gate. Unknown/unsupported/budget-denied paths never take that gate. Concurrent identical first requests can conservatively reserve unused budget slots before request deduplication; they cannot exceed three actual deliveries. The request guard precedes the Person gate, and no budget row lock overlaps that gate. Ready status is rechecked after acquiring it.

Accepted MVP risk: someone knowing the primary contact can exhaust its OTP delivery budget and delay the owner's reset. A private ResetRequestsLimited notification is queued at most once per Person/window for provider alerting. This is not proof of notification delivery. Account recovery has no factor bypass; lost password plus lost recovery code means no automatic reset. Contact release/reassignment, actual provider delivery/alerting and BFF loss/replacement UX are release requirements.

Known and unknown responses have the same shape and perform the same initiation cryptographic operations. Database paths still differ; acceptance smoke records latency samples for known, unknown and suppressed paths. Initial small CI samples showed a known/unknown timing difference (recorded in VERIFICATION.md). Mitigation and representative adversarial timing acceptance are required before real-user release. This observation is not a constant-time or production load certification. Real BFF distributed refresh single-flight, eligibility mutation epoch/revocation, audit/event retention and throughput testing remain release gates.
