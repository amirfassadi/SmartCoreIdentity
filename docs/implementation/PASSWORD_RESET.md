# Development dual-factor password reset

Migrations 009–010 and OpenAPI 0.6.0 complete the selected primary-contact OTP plus pre-enrolled 128-bit recovery-code policy for email and telephone accounts. The existing RecoveryEnrollmentEnabled opt-in controls enrollment, initiation and completion. Development-only, real-user release remains blocked. Stop older application instances before applying migrations 009–010; older enrollment/initiation writers are not compatible with the new reservation/decoy schema.

POST /auth/password/reset/complete requires the authenticated BFF/subject and operationId, challengeId, bindingSecret, eight-digit code, 32-hex recoveryCode, and a 15–128-character newPassword. No Bearer Session or caller-supplied verified flag is accepted. Both proof comparisons are constant-time; failure is the same UNAUTHORIZED response. Five failed presentations per Person window are shared across challenges and replay; creating a fresh challenge does not reset that counter. Each exhausted window causes a persisted cooldown of 15, 30, 60, 120, 240 and then at most 360 minutes. Escalation resets after 24 hours without a counted failure. Requests during cooldown do not extend it or reset the failure counter. Each cap crossing atomically queues one ResetProofFailuresLimited notice; repeated denials create no extra notices. Each fresh challenge permits five presentations. Invalid password policy is rejected before any fence. Counter transactions finish before the Person gate; Argon2 runs without locks.

Under the Person gate, proof expiry, contact binding, enrollment version, unreserved code, epoch, readiness and unchanged Credential evidence are checked again. The shared password-change admission writes a ResetPassword intent and sealed recovery/replay Argon2 material, reserves the code, advances epoch once and closes Sessions/families atomically. OTP delivery material is erased on acceptance. Credential replacement and its immutable receipt/PasswordChanged outbox commit independently without holding a Session lock. The selected event context is documented in RESET_EVENT_DECISION.md.

Only receipt-backed Reconciled releases the fence. Applied consumes the reserved code and queues PasswordResetCompleted once; terminal RejectedNotApplied releases its reservation without consuming it. FailedClosed preserves both fence and reservation until private operator recovery obtains a receipt; no timeout or force unlock exists. New login with the new password reports recoveryEnrollmentRequired=true. Re-enrollment requires a fresh active Session at the reset epoch, current-password proof and explicit loss acknowledgement; a database trigger rejects an older Session. BFF must require replacement before ordinary use.

Identical lost-response replay is bound to client, operation, challenge and both original factors with a purpose-specific MAC containing no password. The new password is compared against sealed Argon2 material outside locks. Replay cannot outlive the original ten-minute challenge. Accepted challenge/receipt evidence is retained; expiry never undoes an accepted operation or blocks its worker reconciliation.

## Initiation storage and contention

Unknown, unenrolled, ineligible, fenced and budget-denied initiation stores only a deletable ten-minute decoy. Known eligible challenges keep immutable bindings; unaccepted expired challenges and their delivery/attempt rows are deleted. Worker cleanup removes at most 100 decoys and 100 eligible unaccepted challenges per tick. Accepted challenges are retained by their immutable acceptance foreign key. Sustained-volume storage monitoring and historical accepted-operation retention remain release work.

The per-Person three-deliveries/fifteen-minute budget is reserved in an autocommit transaction before taking the Person gate. Unknown/unsupported/budget-denied paths never take that gate. Concurrent identical first requests can conservatively reserve unused budget slots before request deduplication; they cannot exceed three actual deliveries. The request guard precedes the Person gate, and no budget row lock overlaps that gate. Ready status is rechecked after acquiring it.

Accepted MVP risk: someone knowing the primary contact can exhaust its OTP delivery budget and delay the owner's reset. A private ResetRequestsLimited notification is queued at most once per Person/window for provider alerting. This is not proof of notification delivery. The proof failure cap likewise permits denial of recovery when an attacker has an eligible challenge. Escalation reduces OTP guesses with a leaked recovery code but increases that denial window to at most six hours per saturated window; an active attacker can repeatedly deny recovery. This tradeoff is explicit, with no operator proof bypass; login remains available and no fence is created by failed proof. Account recovery has no factor bypass; lost password plus lost recovery code means no automatic reset. Contact release/reassignment, actual provider delivery/alerting and BFF loss/replacement UX are release requirements.

Both initiation and completion select a common 200–220 ms response deadline before account/challenge lookup. The deadline is independent of account existence, eligibility, proof validity and budget state; it is not a random delay added on top of execution time. Waiting occurs only after connection/transaction disposal. Within this processing budget, real, decoy and suppressed failures wait to the same deadline distribution. Work exceeding it returns after completion and increments reset.response_deadline_overruns, tagged only with endpoint and success/failure. Load/lock contention can exceed the deadline and reveal database-path timing: this mitigation is not unconditional enumeration resistance. Controlled CI acceptance measures both endpoints against PostgreSQL (12 samples per real/decoy/suppressed group), with a 190 ms lower tolerance, 300 ms service maximum, p50 spread under 35 ms and p90 spread under 60 ms; HTTP initiation and completion additionally permit at most 350 ms including transport, with 12 samples/group on each route. Fresh eligible initiation is covered by the service acceptance; HTTP covers bound real replay, fresh decoy and budget-suppressed initiation. Representative adversarial/load testing and failure-overrun monitoring are still mandatory before public release. Real BFF distributed refresh single-flight, eligibility mutation epoch/revocation, audit/event retention and throughput testing remain release gates.

## Input and upgrade compatibility

The API trims surrounding whitespace and accepts either ASCII hex case for recovery codes before computing verifiers/receipt MACs. Display remains uppercase; BFF should offer the same input handling. It never normalizes either password. Newly generated reset OTPs are uniformly selected from 100 million eight-digit values, including leading zeros. Registration/setup OTP policy is unchanged. Migration 010 preserves otp_digits=6 for existing delivery rows, defaults new deliveries to eight and checks submitted length against that row. Legacy accepted receipt replay keeps its original ten-minute bound; legacy six-digit challenges cannot be renewed into longer-lived six-digit proof.
