# Development authentication runtime — 2026-10-10

Architecture A: Credential evidence is read without locks; Session commits acquire the Person issuance gate and never acquire `credential:*`. Registration Credential/Ready/ack transactions remain separate. Pending mutation, epoch mismatch, inactive Person, non-Ready registration or absent/inactive Credential deny issuance. Login verifies Argon2 using fixed supported work factors and rechecks the preverification epoch and Credential identity/hash under the gate before writing a Session. Unknown-contact login performs the same KDF work and returns the same outward unauthorized shape. Per-process HTTP admission remains a development limit, not distributed abuse enforcement.

## Opt-in surface

`Identity__AuthenticationEnabled=true` enables POST `/auth/login`, GET `/me`, POST `/auth/refresh` and POST `/auth/logout`. Default is disabled. All four require `X-Bff-Client-Key` matching `Identity__BffClientKey`; self/logout additionally require signed access Bearer. This is an authenticated **test BFF adapter**, not a browser cookie/CSRF implementation or production confidential-client authorization. No token is intended for browser JavaScript. The app continues to refuse Production startup. Reset endpoints do not exist. Password change and development operator recovery require the additional flag described below.

Set a separate 32-byte base64 `Identity__AccessSigningKey`, distinct from the existing MAC/material keys, and a BFF client secret at least 32 characters. No values are committed. This development issuer uses standard IdentityModel JWT signing/validation (HS256 only, fixed issuer/audience, signature and lifetime checks, zero clock tolerance). The current key-version identifier is development-v1; managed rotation/JWKS/resource-server integration is still release work. The JWT package is pinned in dependency locks. [Microsoft JWT validation guidance](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-jwt-bearer-authentication?view=aspnetcore-10.0) is an implementation reference, not security approval of this custom development protocol.

The closed development wire subset is [authentication OpenAPI](../../contracts/authentication.openapi.yaml). Login accepts exactly one email/mobile and password, returning person and Session tokens. `expiresAt` is immutable Session expiry (login +86400 seconds); separate `accessExpiresAt` is at most issuance +900 seconds and never beyond Session expiry. Access expiry is rounded down to whole JWT seconds. Adding the separate deadline and required foreground assertion is a versioned development contract, not a silent change to upstream consumers.

Refresh requires `{refreshToken, foreground}` with foreground explicitly present and asserted by the authenticated test BFF. Current generation is consumed and one successor committed atomically with the internal RefreshTokenRotated fact. Only a successful foreground refresh updates idle evidence. Background rotation never extends the 30-minute foreground idle deadline. Absolute expiry never moves. Wrong-client or guessed secret does not revoke another family; a verified consumed predecessor before deadline closes its Session/family and commits RefreshTokenReuseDetected plus a separate latency observation. Grace is zero, including lost-response retry. Already revoked/expired families are uniformly unauthorized, with no successor disclosure. Concurrent presentations yield at most one successor, and the losing spent presentation revokes the family under the selected strict policy.

`/me` checks current Session/family eligibility, epoch and Person/Credential/Ready online. It does not renew idle. Logout binds request SessionId to the signed proof, closes Session/family atomically and writes one LogoutCompleted fact; same bound terminal replay returns 204 without rewriting closure evidence. Deadline expiry is recorded lazily on authenticated refresh/self/logout, with one SessionExpired fact; no autonomous Session sweeper is claimed. General external self-contained access may remain valid until JWT expiry; this adapter's online checks do not claim universal immediate invalidation.

## Events and measurement

Authentication public facts stay in a separate unpublished `auth_domain_event_outbox` because registration's unique registration/event key cannot represent repeated Sessions. LoginFailed preserves the pinned restricted Security-event contract, including contact and internal reason, while outward errors remain uniform. No failed-password value, JWT, refresh secret or verifier enters event payloads. Access logs must not be configured to capture sensitive headers/body. No broker/T16 delivery or real consumer compatibility is claimed.

Refresh security facts retain exactly the existing internal schema; they are separate from public facts/T16. The reuse latency observation is not proof of theft or lost response and does not enable grace. Audit retention and operational metric ownership must be selected before deployment; no automatic production audit purge is configured.

## Conditions before connecting a real BFF

- **Authentication admission:** replace the shared registration/IP bucket with a separately budgeted, distributed authentication policy. Behind a BFF, `RemoteIpAddress` represents the BFF, so the current 30/minute bucket limits the whole client. Use authenticated client identity plus bounded, trusted end-user admission evidence; never trust an arbitrary browser header or use raw contact as a partition key. Budget login/KDF separately from refresh/self/logout. Per-account throttling must not persistently lock an account merely because someone submits its contact; include source/client budgets, bounded partition cardinality, expiry, uniform responses and abuse monitoring. Prove that independent users behind one BFF do not exhaust each other's ordinary traffic budget and that spoofed partition evidence cannot bypass limits. Exact production budgets remain to be measured; this document does not claim the current limiter has been fixed.
- **Eligibility transitions:** every future Person/Credential eligibility writer must use the mutation serialization protocol, durably advance epoch or irreversibly close all Sessions/families, and reconcile before issuance resumes. Deactivation followed by activation must never revive old access proofs or refresh generations. Direct status toggles are forbidden. Today's schema accepts only Active and exposes no deactivation route; deny-on-read alone is not sufficient when a status lifecycle is introduced. `EligibilityLost` is a reserved close reason, not implemented transition coverage.
- **Refresh single-flight:** the BFF must serialize rotation for each Session across all its instances, atomically store the successor before releasing ownership, and test races, instance crash, lost response and failover. A lock alone cannot recover a successor whose Identity response was lost. With zero grace, never retry the consumed predecessor automatically; require reauthentication after an uncertain outcome. The current same-generation race test deliberately proves family closure, not BFF compatibility.
- **LoginFailed budget and privacy:** unknown contacts also generate restricted outbox facts containing contact. Before real users, set auditable volume/storage caps, retention/deletion ownership and access control. Bound admission before KDF/event creation; define aggregation/sampling without silently changing the pinned event contract or dropping required audit facts. Load tests must measure attacker-driven row growth and account enumeration. No production retention or aggregation exists today.
- **Self-read contention:** `/me` currently takes the exclusive Person gate, locks its Session and may initialize issuance state or persist expiry. Measure concurrent reads, writer latency and tail latency per Person. A shared/read path needs a separate design that preserves epoch/fence consistency and sends lazy-expiry writes through an exclusive path; no performance improvement is claimed here.

## Remaining password lifecycle (delivery gate)

The additional `Identity__PasswordChangeEnabled=true` development slice implements authenticated password change, a scheduled reconciliation worker and a separately keyed loopback operator adapter. See [password-change protocol](PASSWORD_CHANGE.md). It is disabled by default and requires authentication plus a distinct `Identity__AuthOperatorKey`. Reset proof/delivery/completion is still absent; password-change recovery tests do not establish reset safety or resolve reassigned-number recovery. Real-user onboarding stays closed until reset is delivered/accepted and release conditions above pass.

## Verification

The C# harness includes immutability regressions and authentication tests for Ready admission, uniform errors, signature/client rejection, generation rotation/reuse and races, logout replay, access/idle/absolute boundaries, foreground/background behavior, persistent fence denial and resolved-epoch eligibility. Internal mutation fixtures do not perform actual Credential replacement. `scripts/auth-smoke.py` exercises the real ASP.NET process with OpenAPI response checks, BFF admission, strict input, login/self/refresh/reuse/logout; the CI workflow runs it after existing registration/setup smokes. Actual outcomes are recorded in [verification](VERIFICATION.md), not inferred from configured checks.
